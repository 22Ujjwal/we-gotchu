# Shared contract draft

Version: 0.1 draft.
Status: proposed, requiring team review before implementation.
The transaction owner maintains the shared schemas and integration fixtures.
All consumers use those schemas rather than separate copies.
See [ownership](team/ownership.md) for changes and [architecture](architecture-draft.md) for system boundaries.

## Common conventions

Identifiers are opaque strings generated by the server.
Money uses integer minor units and an ISO currency code; the initial demo uses one currency per event.
Timestamps use ISO 8601 UTC, while the brief and supplier terms retain the event's IANA timezone.
Every response carries contractVersion, eventId where applicable, and requestId.
Evidence records contain a source, provider reference, observedAt, and a redacted receipt or confirmation reference.
Every external record carries mode as live or simulated.
A simulated result cannot satisfy a live prerequisite.

Kinds initially include venue_booking, item_purchase, supplier_message, venue_cancellation, and item_cancellation.
Supplier message approval must specify recipient, purpose, and the reviewed content or permitted content bounds.
Separate read-only research from those action kinds.
Candidate availability and price estimates are not guaranteed quotes.
Recheck exact commitments before execution; a changed supplier, time, quantity, terms, or approved total requires a revised plan and approval.

## API commands and queries

All routes below are proposed under /api/v1.
Every route enforces customer ownership on the server.
Every mutation accepts an Idempotency-Key and validates the expected revision where state already exists.

| Route | Input | Result |
| --- | --- | --- |
| POST /events | EventBrief input | Created EventSummary with missing fields. |
| PATCH /events/:id/brief | expectedRevision and changed brief fields | New brief revision and invalidated old proposal. |
| POST /events/:id/research | expectedRevision | Accepted jobId; no supplier commitment. |
| POST /events/:id/plans | selected candidate IDs and expectedRevision | Server-validated proposed EventPlan. |
| POST /events/:id/approvals | planId and exact planRevision | Stored Approval and payment-ready state. |
| POST /events/:id/checkout | approvalId and expectedRevision | Checkout URL for the approved total. |
| POST /events/:id/cancellation-quotes | commitmentIds | Current terms, maximum loss, expected refund, and expiry. |
| POST /events/:id/cancellations | quoteId and accepted terms revision | CancellationApproval and accepted jobId covering both commitments. |
| GET /events/:id | None | Latest authoritative EventSummary. |
| GET /events/:id/progress?afterSequence=N | Last sequence | Ordered progress entries and latestSequence. |

Payment webhooks are provider-authenticated server endpoints, not customer approval routes.
Return 202 for accepted asynchronous work rather than reporting it completed.
Use 409 for stale revisions or conflicting reuse of an idempotency key, 422 for invalid input, and 403 for unauthorized commands.
Return errorCode, a customer-readable message, retryable, and the current revision when appropriate.
Never include raw supplier credentials in an error.

## Internal supplier adapter

Research accepts the brief and returns candidates with evidence.
Quote accepts an exact target and returns price, availability, terms, and expiry.
Execute accepts an approved action reference and stable execution key, then returns an ActionResult.
Reconcile accepts the action and known supplier references and returns the observed result without creating a new purchase.
Cancel accepts a commitment reference and cancellation approval and returns a cancellation ActionResult.
ReadRecovery returns supplier reversal or refund evidence separately from cancellation state.

The agent owner implements supplier interaction inside these adapters.
The transaction owner validates permission and claims an execution attempt before calling an adapter.
Neither a public MCP tool nor an agent callback can bypass that transaction check.
Keep the same contract for live and simulated adapters, with explicit mode on every result.

## State and concurrency rules

Action states are queued, running, awaiting_input, succeeded, failed, outcome_unknown, and skipped.
Only supplier evidence establishes succeeded for a commitment or cancellation.
A timeout after an external call becomes outcome_unknown until reconciliation proves success or failure.
Do not retry an unknown purchase as a new purchase.

Customer payment states are pending, succeeded, failed, and canceled.
Customer refund states are requested, pending, succeeded, and failed.
Supplier recovery has its own pending, succeeded, and failed state and money amount.
EventSummary displays these independently and derives a partial outcome when only some actions succeed.

Persist the command and a request-body hash under the customer's idempotency key.
An identical retry returns the existing result; a different body under that key returns a conflict.
Use stable provider keys where supported and a database uniqueness constraint for action execution.
A worker lease alone cannot prove an external call never ran after a crash.
Reconcile expired attempts before re-executing them.

Payment verification and approval checks must match event, revision, currency, amount, and mode.
Deduplicate provider webhook IDs and tolerate out-of-order delivery through provider-state reconciliation.
A payment arriving after approval revocation must not trigger supplier work.
Record it for the refund policy instead.

Cancellation revokes permission for unstarted commitments and creates cancellation work for confirmed commitments.
An in-flight commitment remains unresolved until evidence is available, then the cancellation policy applies.
Canceling a Naive session is not canceling a venue or an order.
No atomic transaction spans both suppliers, so record each independently.

## Shared fixtures and compatibility

The transaction owner publishes fixtures for a proposed event, paid event, two successful commitments, partial commitment, unknown outcome, cancellation in progress, and refund pending.
The frontend and agent owners review these before implementing against them.
Fixtures are simulated and must say so.
Breaking contract changes require a version change and agreement from both consumers before integration.
Optional additive fields can retain the version if existing consumers still work.
